The true decimal peers are rust_decimal and fpdec. Every claim below was checked against source (src/d64.rs, src/d96.rs, Cargo.toml) or the peers' published docs on 2026-06-20.

c In fixed-point, mul_add(a,b,c) = trunc(a·b/SCALE) + c: the product is reduced once (one truncation) and the add of c is exact. So fixdec's mul_add is identical in result to mul then add — it is an ergonomic/overflow convenience, not a precision win like float FMA (which rounds the whole a·b+c once). rust_decimal and fpdec expose no mul_add at all.
d Transcendentals were deliberately removed: a correct sqrt on D96 needs 256-bit intermediates (the exact multiply only fits i128 because the mantissa is capped at 96 bits), and on a fixed 8/12-dp scale the result is precision-limited regardless. 3. Correctness notes that matter more than the checkmarks

3.1 Truncation, not banker's rounding, in × and ÷

fixdec multiply/divide truncate the sub-scale remainder toward zero. This is fast, deterministic, and consistent — but it is a real semantic difference from rust_decimal, which rounds half-even inside multiply. For example a product whose exact value is …·xated.5 at the last representable digit lands one ulp lower in fixdec than in rust_decimal. Neither is "wrong", but a system mixing the two must pick one as the source of truth. This behaviour is currently undocumented in the public API and should be.

3.2 percent_of / add_percent double-truncate

percent_of is checked_mul(pct).checked_div(HUNDRED) — i.e. trunc(trunc(self·pct/SCALE)/100): two independent truncations. A fused form trunc(self·pct/(SCALE·100)) truncates once and can differ by 1 ulp. For D64 the fused product fits i128 trivially; for D96 it can route through the existing 192-bit divide. Small, but it is the kind of ≤1-ulp inconsistency an "exact, auditable" library should not have. (An earlier draft mislabelled this "two banker's roundings" — it is two truncations.)

3.3 Canonical bytes are a genuine, underexploited edge

Because fixdec normalises, D64/D96 are the only types here where byte-equality implies value-equality. That makes them ideal map keys, dedup keys, and wire identifiers — rust_decimal's 1.5 vs 1.50 hash differently. Worth stating explicitly in the docs as a feature, not an accident.

4. Zero-copy: rkyv vs bytemuck / zerocopy

These solve different problems and the matrix's single "zero-copy" cell hides that. The short version:

Aspectbytemuck / zerocopyrkyv
What it is Trait-based transmute: reinterpret a value's existing memory as &[u8] and back. A full zero-copy (de)serialization framework ("archival").
Works on Only fixed-layout plain-old-data (no padding, no pointers, fixed repr). A repr(transparent) i64/i128 like D64/D96 is the ideal case. Arbitrary graphs: Vec, String, HashMap, Box, nested structs/enums — via a separate Archived<T> layout with relative offsets.
The bytes are… …literally the in-memory value. No transformation, no allocation, no schema. …a distinct archived representation written by a serializer; read in place with no decode pass.
Endianness Native-endian (so fixdec adds explicit write_le_bytes/read_le_bytes for portable wire I/O). Configurable; archived primitives can be endian-explicit.
Validation of untrusted bytes zerocopy separates "any bit pattern valid" (FromBytes) from "safe to view as bytes" (IntoBytes); bytemuck has CheckedBitPattern. bytecheck / rkyv-safe validates a buffer before access.
Cost / weight Effectively free; a derive and a cast. Heavier: derives, archived types, optional validation. Overkill for a lone scalar.
fixdec relevance The right tool today. D64/D96 are their bytes; bytemuck + zerocopy + explicit LE cover it fully. Only relevant as interop: letting a D64/D96 be a field inside someone else's rkyv-archived message.
Why one important nuance favours zerocopy over bytemuck for D96. Not every 128-bit pattern is a valid D96 (the value must stay within ±(295−1)). zerocopy lets D96 derive IntoBytes (always safe) without FromBytes (which would let any 16 bytes become a D96 and bypass the range invariant). bytemuck's Pod is all-or-nothing, so D96 uses NoUninit (write side) rather than Pod. That asymmetry is the whole reason both crates are wired up rather than just one.

Takeaway for the roadmap: rust_decimal and fpdec both ship an rkyv feature precisely so they can live inside archived structures. fixdec does not — so a trading system that memory-maps rkyv message logs cannot embed a D64/D96 without a manual wrapper. That makes an optional rkyv (and arguably borsh) interop feature a legitimate, well-scoped gap (P2 below), distinct from the transmute support fixdec already has.

5. Missing features (prioritized)

PriFeatureWhy it mattersNotes / tractability
P0 Selectable rounding modes Top blocker for regulated finance: tax = HALF_UP, IFRS = HALF_EVEN, venue tick rules differ. Both decimal peers have it; fixdec is banker's-only. Tractable — rounding is centralized in internal.rs. Add a mode param + round_dp_with/checked_div_with; keep banker's the default. Avoid fpdec's thread-local mutable default — it kills determinism, fixdec's core selling point.
P0 d64! / d96! literal macro Both peers ship one. Today constants need new(i,f) or runtime from_str. macro_rules! over the existing const fn new; reject >8/>12 dp at compile time.
P0 quantize(tick) + abs_diff Tick-snapping ($0.05 increments) and spread/slippage are bread-and-butter for trading. fpdec has Quantize; fixed has dist. quantize must round the quotient in one fused step — do not reuse the double-truncating percent_of pattern (§3.2).
P1 round_dp with negative places Round to nearest 10 / 100 for notional and lot sizing. Natural extension of the rounding rework in P0.
P1 MIN_POSITIVE / STEP const The smallest representable increment (from_raw(1)) is useful for tolerances and tick math. Name it STEP/MIN_POSITIVE, not EPSILON — misleading on a fixed-scale type.
P2 rkyv (and borsh) interop feature Both peers have rkyv; without it a D64/D96 can't be a field in an archived message log (§4). Optional, additive feature; no API change to existing transmute support.
P2 rem_euclid / div_euclid / copysign Parity with the numeric-tower conventions users expect. Thin wrappers over existing ops.
P3 Transcendentals (sqrt/ln/exp/powf/trig) rust_decimal/f64 cover this; demand on a fixed 8/12-dp money type is low. Do not chase. Needs 256-bit intermediates and is precision-limited at fixed scale (footnote d). Bridge to rust_decimal/f64 instead.

6. Improvements to existing features

  1. Document the truncating mul/div policy (§3.1) — the biggest accuracy finding. At minimum document it; surfacing it next to rust_decimal's round-half-even multiply prevents silent cross-system disagreement.
  2. Fuse percent_of/add_percent to a single truncation (§3.2) — removes a ≤1-ulp inconsistency; D64 fits i128, D96 routes through existing 192-bit helpers.
  3. De-duplicate the D64/D96 arithmetic core — ~10.5k near-identical lines; internal.rs already calls the duplication "the root cause of several bugs". Macro-generate the bug-prone twins (mul/div/rescale/round) via a define_decimal!, keep type-specific surface (constants, 96-bit clamp, byte I/O) hand-written, and add a parity test suite running identical property tests against both types.
  4. Parameterize the internal rounding helpers now (even before exposing P0 modes) so ceil/floor/trunc/round share one path and the public modes API is a thin wrapper; keep an #[inline(always)] banker's fast path so existing sites pay nothing.
  5. Promote canonical bytes (§3.3) as a documented feature — it's a real edge over both decimal peers and is currently invisible.
  6. Keep the fixed-scale design; document the escape hatch — const-generic precision would explode the byte/serde/pyo3 surface. Instead document: use D96 vs rust_decimal when you need >12 dp, >±3.96e16, or transcendental math — the to_d96/to_rust_decimal bridges already make this smooth.

7. Verdict — when to choose which

Where fixdec already wins, and should stay in its lane:

  • Determinism & canonical identity — no NaN/∞/−0.0, total Ord/Eq/Hash, byte-equal ⇔ value-equal. Beats rust_decimal and fpdec.
  • Latency & size — repr(transparent) i64 is the fastest exact-decimal option in the benchmark and the smallest footprint. Beats everyone but raw f64/fixed (which aren't decimal-exact).
  • Safe-by-default serde — exact strings, refuses ambiguous bare floats.
  • Domain fit — basis points, bond ticks, percentages, pyo3 ↔ decimal.Decimal, and a rust_decimal bridge, all in one crate.

Where the peers still win: rust_decimal for ecosystem breadth (SQL drivers, 6 serde modes, maths, rkyv/borsh, wider range) and selectable rounding; fpdec for flexible scale + rounding modes; fixed/f64 for raw speed and transcendental math where binary inexactness is acceptable.

Invest, in order: (1) selectable rounding modes, (2) a d64!/d96! macro, (3) document/fix the truncating mul-div + percent_of double-truncation, (4) de-duplicate the D64/D96 core, (5) optional rkyv interop. Skip the transcendental suite.
